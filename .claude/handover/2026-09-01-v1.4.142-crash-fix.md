## 根因（证据链）
- 141 首次把 3 个 TikTok Swift 私有网络层类名明文放 dylib：
  `PNSFoundationImpl.PNSNetworkHTTPFilterRequest` / `PNSFoundationImpl.PNSNetworkHookManager` / `PumbaaNetworkCore.NetworkEngineUnit`
- TikTok 启动早期反 hook 检测扫描到 → **主动 SIGTRAP 自杀**（安静自杀，无 TikTok 自身错误日志）
- 时序：+load 完成 → 网络栈初始化 → kernel Corpse allowed → launchd termination (2,5,5)
- 排除项：签名链长度（139 短链能跑）、包结构、主二进制差异、load commands、启动路径机器码（950+/954 一致）
- 对照铁证：g139/g140 无任何 PNS 字符串 → 能跑；g141 满屏明文 → 崩

## 关键决策
1. **XOR(0x5A) 混淆类名字符串**，运行时 `xnDecodeXOR()` 还原，dylib 无明文
2. **🔴 clang -O2 常量折叠陷阱**（本次最大踩坑）：XOR 解码函数如果可内联，编译器会**在编译期把解码结果算出来**，
   分块写进 `__literals` 常量池（`ldr q0, 0x66570` 向量化），明文碎片照样进 dylib = 混淆失效。
   **必须三重防折叠**：`__attribute__((noinline))` + `volatile unsigned char key` + `const volatile unsigned char *p` 读取。
   （首版只加 XOR 没防折叠 → grep dylib 仍见 `PNSFoundationImpl.PNSNetworkHTTP` 碎片，反汇编 5bb08 定位到折叠展开，加三重保险后清零）
3. 类名 `PnsRequestHooks` → `XNRequestHooks`（去 "Pns" 敏感子串），文件同步改名
4. NSLog/message/注释清理 PNS 明文
5. 编码串不含 `\x00`（strlen 截断）

## 代价/副作用
- XOR 混淆 + noinline/volatile 阻止了编译器优化，解码是纯运行时循环（每次 install 一次，开销可忽略）
- 编码串留在 dylib（乱码无害），但若 TikTok 更新检测算法（如扫 XOR 模式）需换 key/算法
- net_request 的 hook 对象是 `NSClassFromString` 懒加载类，若类名随 TikTok 版本变化需重采
